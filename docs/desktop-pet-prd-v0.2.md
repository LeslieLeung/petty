# Desktop Pet PRD v0.2

## 1. 文档信息

- **产品名称**：Desktop Pet
- **文档版本**：PRD v0.2
- **目标平台**：macOS / Windows
- **客户端技术方向**：Tauri 2 + PixiJS
- **资源生产方式**：离线生成，不内置于客户端
- **资源来源**：基于 hatch-pet 流程产出的桌宠资源包，并扩展为可扩展状态的资源包规范

---

## 2. 产品概述

Desktop Pet 是一款运行在 macOS 和 Windows 上的跨平台桌宠客户端。用户可以导入离线生成好的桌宠资源包，让宠物常驻桌面、播放动画、响应点击与拖拽等互动，并在后续逐步扩展为具备聊天、陪伴、语音、记忆和人格设定能力的 companion。

本产品的核心边界是：

1. **客户端只负责运行、渲染、交互和管理桌宠**
2. **桌宠资源通过离线流程生产**
3. **客户端兼容现有 hatch-pet 产物，并提供一套可扩展的资源包规范 v2**

产品目标不是在应用内“生成宠物”，而是让宠物能够稳定、自然、低打扰地“活在桌面上”。

---

## 3. 背景与问题

现有 hatch-pet 更偏向“资源生成与打包”，其核心产物是 `pet.json` + `spritesheet.webp`，围绕固定 atlas、固定 cell、固定状态集合和质量校验展开。这种方式适合作为资源生成链路的终点，但并不足以直接支撑一个桌宠产品。

若要做成桌宠客户端，仍需补齐以下产品层能力：

- 面向桌面使用场景的交互设计
- 可扩展状态系统，而不是绑定固定状态名
- 行为调度与生命周期管理
- 资源包版本管理与兼容机制
- 屏幕边缘 / 窗口边缘等环境交互能力
- 面向未来聊天、ASR、TTS、SOUL.md、记忆的扩展接口

因此需要一个独立的客户端 PRD 和运行时资源规范。

---

## 4. 产品定位

### 4.1 一句话定位

一款可导入自定义资源、支持桌面陪伴和后续 AI 扩展的跨平台桌宠客户端。

### 4.2 核心价值

- 让角色真正“活在桌面上”
- 提供轻互动、低打扰的陪伴感
- 支持资源扩展和行为扩展
- 为未来人格化 companion 能力预留统一入口

### 4.3 产品原则

- **运行优先**：先把桌宠稳定跑起来，再叠加智能能力
- **资源与运行解耦**：客户端不包含生产链路
- **兼容优先**：先兼容现有产物，再演进格式
- **低打扰**：不影响用户正常工作
- **本地优先**：MVP 尽量不依赖云服务
- **渐进增强**：聊天、语音、记忆能力可插拔扩展

## 6. 产品目标

### 6.1 MVP 目标

在 macOS 和 Windows 上提供一个可用的桌宠客户端，支持：

- 导入并加载桌宠资源包
- 桌宠常驻桌面显示
- 基础交互：点击、双击、拖拽、右键菜单
- 基础状态播放与状态切换
- 长时间无交互时的自主行为切换
- 屏幕边缘感知和贴边行为
- 本地设置管理
- 扩展状态机制
- 对旧版 hatch-pet 产物保持兼容

### 6.2 后续目标

在不推翻 MVP 架构的前提下，扩展：

- 窗口级环境感知与窗口边缘交互
- 宠物陪伴与聊天
- ASR / TTS
- SOUL.md 定制人格
- 记忆系统
- 更复杂的行为调度 / needs system / 行为树
- 多宠物与生态能力

- 在客户端内生成宠物图片、动画、spritesheet

## 8. 核心使用场景

### 场景 1：导入桌宠

用户拿到离线生成好的资源包，导入客户端，看到宠物出现在桌面。

### 场景 2：轻互动陪伴

用户工作时宠物在桌面边缘待机、走动、打招呼；点击后会有反馈动作。

### 场景 3：无交互时的自主陪伴

用户长时间不操作宠物时，宠物仍会按自己的节奏切换状态，例如发呆、打盹、睡觉、吃东西、整理自己、巡视环境等，维持“它还活着”的感觉。

### 场景 4：贴边与地面感

宠物在靠近屏幕边缘时，能够识别边界并在底边行走、停留、趴下或贴边休息，形成更自然的桌面存在感。

### 场景 5：窗口环境互动（后续）

用户把宠物拖到窗口附近时，宠物能够识别窗口边缘并在其上方行走、停留、趴下，增强“它真的在桌面里生活”的感觉。

### 场景 6：自定义宠物人格（后续）

用户可给宠物配置 SOUL.md，让宠物的说话风格、反应方式、偏好更一致。

### 场景 7：语音陪伴（后续）

用户按住说话，宠物识别语音、理解上下文、用 TTS 回复。

## 10. 功能范围

# 10.1 MVP 功能

## A. 桌宠基础运行

1. 启动客户端后显示桌宠
2. 桌宠支持透明背景渲染
3. 桌宠可在桌面上移动与播放动画
4. 用户关闭主窗口后，桌宠仍可继续驻留
5. 支持开机自启动（可选开关）

## B. 宠物资源管理

1. 导入本地桌宠资源包
2. 查看当前已安装宠物列表
3. 切换当前激活宠物
4. 删除已安装宠物
5. 资源包版本校验
6. 对不兼容资源给出明确错误提示

## C. 基础交互

1. 单击：触发轻反馈
2. 双击：触发强反馈 / 特殊动作
3. 拖拽：移动宠物位置
4. 右键：打开宠物菜单
5. 悬停：显示名字或简单气泡（可选）

## D. 基础状态系统

MVP 至少支持以下状态类别：

- `idle`：待机
- `greet`：打招呼
- `walk` / `move`：轻移动
- `run-left` / `run-right`：定向移动
- `jump`
- `sleep`
- `doze`
- `eat`
- `groom` / `clean`
- `rest`
- `observe`
- `react-happy`
- `react-annoyed` / `poke`
- `review` / `work`
- `failed`

说明：
客户端需要在兼容现有 hatch-pet 状态的基础上，建立更通用的状态模型，而不是把状态名写死在代码中。

## E. 状态切换与行为调度

1. 空闲时自动在若干状态间切换
2. 点击时触发交互状态
3. 拖拽时进入被抓取状态
4. 释放后进入落地 / 恢复状态
5. 状态支持优先级与打断规则
6. 状态播放结束后可回到默认状态
7. 长时间无交互时，宠物可按自主行为规则切换到打盹、睡觉、吃饭、整理自己、观察周围等状态
8. 自主行为需支持触发阈值、权重、冷却时间和最短播放时长
9. 用户交互可中断自主行为，并在结束后恢复到合适的待机或移动状态

## F. 边缘与环境基础交互（MVP 范围）

1. 识别屏幕底边、左右边缘和顶部边界
2. 宠物可在屏幕底边行走、停留、趴下或贴边休息
3. 拖动到边缘后可吸附到边缘位置
4. 当宠物失去支撑时，可回退到普通移动、掉落或落地状态
5. 若资源包未定义边缘相关状态，则回退到普通站立或移动状态

## G. 设置

1. 开机自启动
2. 是否显示名字/气泡
3. 宠物大小缩放
4. 宠物音效开关（为未来预留）
5. 屏幕位置锁定
6. 是否允许自动走动
7. 是否启用自主行为
8. 自主行为频率
9. 是否启用贴边行为
10. 当前宠物切换
11. 调试模式（查看状态名、资源信息）

## H. 兼容与回退

1. 支持现有 hatch-pet 产物直接导入
2. 若资源为旧格式，则走兼容模式
3. 若缺少扩展字段，则用默认行为补齐
4. 若缺失某个状态或边缘行为，则进行功能降级而不崩溃

## 11. 用户流程

### 11.1 首次使用

1. 用户安装并启动应用
2. 应用提示导入桌宠资源包
3. 用户选择本地资源包
4. 应用校验资源包
5. 校验成功后显示宠物
6. 弹出简短引导：拖动、点击、右键菜单

### 11.2 日常使用

1. 应用后台常驻
2. 宠物按默认节奏播放状态
3. 长时间无交互时，系统触发自主行为
4. 用户点击或拖动进行互动
5. 用户通过右键菜单切换宠物或打开设置

### 11.3 边缘行为

1. 宠物移动到屏幕边缘附近
2. 系统识别可停留的边缘
3. 宠物吸附并切换贴边/停留/边缘移动状态
4. 若离开边缘或失去支撑，则恢复普通状态

### 11.4 切换宠物

1. 右键菜单打开“宠物库”
2. 用户选择另一个宠物
3. 客户端卸载当前宠物资源
4. 加载新宠物资源并恢复到默认位置或记忆位置

## 13. 资源包规范（产品定义 v2）

这是客户端侧最关键的规范之一。目标是：

1. 兼容现有 hatch-pet 产物
2. 支持新增状态和新增交互，而不是把逻辑写死在客户端里
3. 为未来聊天、语音、记忆和环境交互预留能力声明

### 13.1 资源包目录

```text
pet-package/
  manifest.json
  sprites/
    main.webp
  meta/
    soul.md            # 可选，非 MVP 使用
    thumbnail.png      # 可选
  audio/               # 可选，未来使用
```

### 13.2 manifest.json 必须包含

- `version`：资源格式版本
- `id`：宠物唯一标识
- `name`：宠物展示名
- `description`
- `defaultScale`
- `canvas`
  - `cellWidth`
  - `cellHeight`
  - `sheetWidth`
  - `sheetHeight`
- `defaultState`
- `states`
- `transitions`
- `interactions`
- `anchors`
- `capabilities`

### 13.8 兼容策略

#### 兼容旧 hatch-pet 资源

若导入的是旧版 `pet.json + spritesheet.webp`：

- 客户端读取旧格式
- 自动映射到内部统一模型
- 若状态缺失，则只启用可识别状态
- 若没有 `manifest.json`，则生成运行时兼容描述

#### 新版资源

新资源优先使用 `manifest.json`，不再要求客户端依赖固定状态集合。

## 14. 状态系统设计要求

客户端内部需要一套统一状态机，至少支持：

### 14.1 状态分类

- 常驻状态：`idle`、`sleep`
- 移动状态：`walk`、`run-left`、`run-right`、`jump`
- 交互状态：`greet`、`pet`、`poke`
- 情绪状态：`happy`、`sad`、`angry`、`curious`
- 自主状态：`doze`、`eat`、`groom`、`observe`、`rest`
- 功能状态：`work`、`review`、`chatting`、`listening`、`speaking`
- 环境状态：`edge-stand`、`edge-walk`、`edge-lie`、`hang`、`fall`、`land`

### 14.2 状态属性

- 优先级
- 是否可被打断
- 最短播放时长
- 冷却时间
- 进入条件
- 退出条件
- 后继状态
- 是否需要地面或边缘支撑

### 14.3 调度原则

- 无输入时走自动调度
- 用户交互优先级高于自动行为
- 高优先级异常状态可强制回退到 `idle`
- 未来聊天状态优先级高于普通待机

### 14.4 自主行为驱动

- 支持基于“无交互时长”的行为触发
- 支持行为权重和冷却
- 支持同类行为互斥
- 支持被用户输入打断并平滑恢复
- 后续可扩展为简单 needs system（困倦、饥饿、无聊）

### 14.5 环境感知状态

- 支持由环境事件触发状态切换
- 环境事件包括：接触屏幕边缘、接触窗口顶边、失去支撑、落地
- 支持 locomotion state 与 surface state 切换
- 支持窗口移动后的重定位与回退

## 15. 交互需求

### 15.1 点击

- 单击后宠物给出轻反馈
- 反馈动作应在 300ms 内开始
- 若资源包未定义 click 行为，默认播放 `greet` 或 `idle` 变体

### 15.2 双击

- 播放更明显的互动动作
- 后续可绑定“唤醒聊天面板”

### 15.3 拖拽

- 用户可拖动宠物位置
- 拖动时宠物进入抓取/悬空状态
- 松手后宠物播放落下或恢复状态

### 15.4 右键菜单

包含：

- 切换宠物
- 暂停互动
- 打开设置
- 重新加载资源
- 打开数据目录
- 退出

### 15.5 环境交互

- 宠物接近可停留边缘时，可吸附到边缘
- 当检测到窗口顶边时，宠物可切换到边缘站立 / 行走状态（后续）
- 当支撑面消失时，宠物进入掉落或跳离状态
- 若宠物资源未定义边缘状态，则回退到普通站立或移动

### 16.1 聊天入口

### 16.3 记忆

## 18. 非功能需求

### 18.1 性能

- 启动后快速展示宠物
- 长时间挂机时 CPU 占用应低
- 多数时间应保持低频刷新或按状态节流
- 资源切换不能明显卡顿

### 18.2 稳定性

- 单个资源包异常不能导致整个应用崩溃
- 状态缺失应优雅降级
- 图片解码失败应可回退到错误提示
- 环境感知失败时应回退到普通模式

### 18.3 可扩展性

- 新状态无需修改核心渲染代码即可接入
- 新交互事件允许通过配置扩展
- 新能力（chat / asr / tts / memory）可插拔
- 新环境事件（窗口、边缘、地面）可逐步接入

### 18.4 可维护性

- 资源格式版本清晰
- 兼容层独立
- 调试信息可视化
- 平台差异逻辑与通用逻辑明确分层

## 19. MVP 验收标准

满足以下条件即认为 MVP 可发布内测：

1. 用户可成功导入至少一种现有 hatch-pet 资源
2. 宠物可正常显示、播放、点击、拖拽
3. 宠物状态切换稳定，无明显闪烁和错帧
4. 长时间无交互时，可自动切换到至少两种自主行为状态
5. 屏幕边缘贴附与回退逻辑可正常工作
6. 设置可保存并在重启后恢复
7. 资源损坏时能给出明确错误提示
8. 至少支持一种扩展状态资源包
9. macOS 与 Windows 均可运行核心流程

## 21. 风险与待确认项

### 风险 1：资源格式演进

如果直接绑定现有 hatch-pet 固定行列结构，后续扩展状态会很痛，因此必须尽早引入统一 manifest。

### 风险 2：不同资源包质量差异大

离线生成资源质量可能不一致，需要客户端具备更强的容错、降级和调试提示。

### 风险 3：桌面层行为跨平台差异

macOS 与 Windows 对窗口层级、穿透、焦点、托盘等行为存在差异，PRD 层只定义体验目标，实现时需要平台适配。

### 风险 4：未来聊天能力侵入当前模型

如果不在现在预留 capabilities / SOUL / memory 接口，后续会重构资源格式和状态系统。

### 风险 5：窗口环境感知的跨平台实现复杂

窗口边界探测、层级关系、前台窗口变化、多显示器和系统权限在 macOS 与 Windows 上差异较大。需要将“屏幕边缘感知”和“窗口边缘感知”拆分为两个阶段，避免 MVP 范围失控。

## 22. 开放问题

1. MVP 是否需要支持任务栏 / Dock 区域规避
2. MVP 是否默认启用自主行为，还是首次安装时让用户选择
3. 边缘吸附是否需要用户可见的动画反馈
4. v0.2 的窗口感知是否只做前台窗口，还是全部可见窗口
5. 将来聊天面板是独立窗口还是内嵌气泡模式
6. SOUL.md 与资源包的绑定关系是否允许一宠多人格

## 24. 结论

Desktop Pet 的产品核心应围绕“稳定运行、自然行为、资源可扩展”来构建。

MVP 重点是让宠物：

- 能被导入
- 能稳定运行
- 能与用户互动
- 能在无交互时表现出自主行为
- 能对屏幕边缘产生自然反应

v0.2 再进一步强化环境感知，让宠物从“浮在桌面上”演进为“生活在桌面环境里”。
